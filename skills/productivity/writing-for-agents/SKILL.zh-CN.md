[English](SKILL.md) · [简体中文](SKILL.zh-CN.md)

编写任何 agent 会用到的文档的参考资料——一个 skill、一份 `AGENTS.md` / `CLAUDE.md`、一份通过指针访问到的文档。它们的封装方式不同；但写作的道理是相通的：让每一份都可预测的杠杆是同一套——是 agent 每次都走*同一个流程*，而不是产出同一份输出。

当你在写的文档是一个 skill 时，读 [`SKILL-MECHANICS.md`](SKILL-MECHANICS.md) 了解 frontmatter、调用方式的选择，以及 router skills。

## Context pointers

一个 **context pointer** 是 agent 上下文里持有的一个引用，它点名某些不在当前上下文里的材料，并编码了到达那里的条件。一个 skill 的 description 就是一个；`AGENTS.md` 里点名某份文档的一行也是同一种东西。决定 agent 何时能触达这份材料、以及触达得有多可靠的，是这个指针的*措辞*，而不是它指向的目标。一个必须触达的目标背后配了一个措辞无力的指针，这是一个方差 bug：先打磨措辞，只有打磨失败时才考虑把材料内联进来。

一个指针要做两件事——说明这份材料是什么，以及列出应该触发去获取它的那些**分支**（一个分支就是这份文档处理的一种不同情形，让不同的运行走上不同的路径）。一个始终加载的指针，每一个字在每一轮都要花费成本，所以它比正文更值得被狠狠地精简：

- **把主导词放在最前面**——指针发挥触发作用的地方就在这里。
- **一个分支一个触发词。** 给同一个分支改个说法的同义词，本质上是把一个分支写了两遍；把它们合并，只保留真正不同的分支。
- **删掉正文里已经承载了的身份信息。**

## The two loads

你添加的每一份文档和每一个指针，都会花掉两种预算之一：

- **Context load（上下文负担）**——始终加载的材料对 agent 窗口造成的成本：`AGENTS.md` 里的一行、一个 skill 的 description，任何每一轮都占在上下文里的东西，不管它有没有被触发，都在消耗 token 和注意力。
- **Cognitive load（认知负担）**——加在人类身上的成本：有哪些文档存在、什么时候该去找哪一份。人类就是那个索引。这不是一个要去最小化的成本——它是人类主导权的代价；在人类判断真正重要的地方花它，在不重要的地方去掉它。

只能通过一个指针触达的材料，逃过了 context load，代价是那个指针自身占的那一行；完全没有指针的材料，则把全部成本都压在 cognitive load 上。

## Information hierarchy

一份文档由两种内容类型构成——**steps**（agent 执行的一系列有序动作）和 **reference**（按需查阅的定义、规则、事实）——它们可以自由混合：全是 steps（一份菜谱）、全是 reference（一份审查规则、这个 skill 本身），或者两者都有。核心决策是每一块内容在**信息层级（information hierarchy）**上放在哪一级，这是一个按 agent 需要这份材料的紧迫程度排列的阶梯：

1. **In-file step（文件内步骤）**——最高优先级：agent 按顺序要做的事。
2. **In-file reference（文件内参考）**——按需查阅。往往是一组理所当然平铺的同级内容（一份审查规则的每一条都在同一级）——这是一种合理的安排，不是一种坏味道。
3. **Disclosed reference（外置参考）**——被推到一个独立文件里，通过一个 context pointer 触达，只有在这个指针被触发时才加载。范围从同一文件夹下的一个兄弟文件，到任何地方都能存在、任何文档都能指向的完全外部参考。

往下推得太少，顶层就会膨胀；推得太多，就会藏起 agent 真正需要的材料。这个张力就是全部的决策所在。

**Progressive disclosure（渐进式展开）**就是在这个阶梯上往下移——移出主文件、放到一个指针背后——好让顶层保持清晰易读。这主要不是一种 token 优化：它是保护这个层级结构的方式。分支是最干净的展开测试：把每个分支都需要的东西内联，把只有部分分支才会用到的东西推到指针背后。当一份文档有 steps 时，本该被外置的文件内参考会把这些 steps 埋起来，让人是否会注意到它们变成一场掷硬币——这是一个方差杠杆，不只是可读性问题。

**Co-location（就近放置）**是文件内部的配套原则：如果说阶梯决定的是一块内容*放多深*，co-location 决定的就是它落地之后*和什么放在一起*。把一个概念的定义、规则和注意事项放在同一个标题下，而不是散落各处，这样读到其中一部分时，它的邻居也会一并被看到。检验标准：这份文档读起来应该像是专门为 agent 写的文档——分组好的材料读起来就是这样；散落的材料不是。（这和重复不同：重复是在两个地方说同一个意思；散落是把一个意思拆成很多碎片。）

**Sprawl（蔓延）**是这里的另一种失败模式：一份文档单纯太长了，即使每一行都是活的、独一无二的。注意力会在过多的内容里被稀释，每多一行都是多一件要保持相关性的东西。解药就是这个阶梯：把参考内容藏到指针背后，按分支或顺序拆分，让每条路径只携带它需要的东西。

## Steps and completion criteria

每个 step 都以一个**完成标准（completion criterion）**收尾——告诉 agent 这项工作完成了的那个条件。两个属性决定它是不是一个有效的杠杆：

- **Clarity（清晰度）**——agent 能不能分辨出完成和没完成？一个模糊的界限（"理解已经达成"）会招致**过早完成（premature completion）**：在这个 step 真正完成之前就结束它，注意力从"做到位"滑向"做完了"。眼前可见的、还没做的**后续步骤（post-completion steps）**提供了这股拉力；完成标准的清晰度则是抵抗它的力量。按顺序防御：**先打磨这条界限**（局部且成本低）；只有当它天生就模糊不清、*而且*你确实观察到了这种"赶进度"的迹象时，才通过拆分这个序列来把后续步骤藏起来——而且藏起来这一招只有跨越一个真正的上下文边界（一次交接或一次 subagent 派发）才有效；一次内联调用不会清空任何东西，后续步骤依然留在上下文里。
- **Demand（要求强度）**——它要求了多少。"every modified model accounted for（每个被改动的 model 都要被说明）"比"produce a change list（列一份改动清单）"逼出更彻底的工作。要求强度驱动**legwork（体力活）**——agent 在工作过程中做的那些挖掘，隐含在措辞里，而不是被单独写成一个 step——它也不受限于某个具体 step："every rule applied（每条规则都要被应用）"约束的是一整块平铺的 reference，就像"every step done（每个 step 都要完成）"约束一个序列一样，这正是一份全是 reference 的文档依然能带有穷举性要求的原因。

最强的标准既可核对，又要求穷举。

## When to split

把一份文档拆成两份，会花掉两种负担中的一种，所以只有当这次拆分真正值得时才拆：

- **按顺序拆**——当后面的 post-completion steps 会诱使 agent 匆匆带过眼前这一步时，就把这段步骤序列拆开。让它们不在视野内，能逼出更多针对当前任务的 legwork。要提防反过来的情况：把几段序列合并会让每个 step 都看到它后面的那些 step，从而招致过早完成。
- **按调用方式拆**——针对 skill 的特定做法：见 [`SKILL-MECHANICS.md`](SKILL-MECHANICS.md)。

## Leading words

一个**主导词（leading word）**是一个已经存在于模型预训练中的紧凑概念，agent 在跑这份文档时会用它来思考（_lesson_、_fog of war_、_tracer bullets_）。作为一个 token 反复出现，而不是作为一句话反复出现，它会积累出一个分布式的定义，用最少的 token 把整片行为区域锚定住，靠的是调用模型已经具备的先验知识。自创一个新词也可以，只要你把它定义清楚，但一个自造的词调用不到任何先验——一个预训练词免费给你的东西，你得靠定义 token 去买；优先找一个已有的词。

它会锚定两次。在正文里，是*执行*：每次这个词出现，agent 都会调用同一套行为，在平铺的 reference 里，它会把注意力聚焦到一类要寻找的东西上。在一个指针里，是*调用*：当同一个词同时活在你的 prompts、你的文档和你的代码库里时，agent 会把这套共享语言和对应的材料联系起来，更可靠地触达它。

主动去找能用主导词重构的机会。一个在三个地方各自被拼写出来的三元组、一个花一整句话去比划一个想法的指针——每一处都是一段渴望被收进单个 token 的文字：

- "fast, deterministic, low-overhead" → _tight_（一个 _tight_ 循环）。
- "a loop you believe in" → _red_——一个模糊的关卡变成一个二元的可观测状态（这个循环在这个 bug 上要么变 _red_，要么不变）。

你能赢两次：更少的 token，以及一个更锋利的、供 agent 挂靠思考的钩子。假设每份文档都带着一些主导词能退休掉的重复表述——去把它们找出来。

**Negation（否定）**是这个杠杆旁边的一种失败模式：通过禁止来引导，会把被禁止的行为拽进上下文，让它变得*更*容易被调用，而不是更少。*不要想大象*，结果满脑子都是大象；否定词是一个弱修饰语，会被那个被强烈激活的概念盖过去，所以这条禁令读起来一半像是在指示要做那件事。要正面表述你想要的行为——直接说出目标行为（"写单行注释"），这样被禁止的那个行为就根本不会被提起。一条禁令只有在它是一道你没法用正面语言表述的硬性护栏时，才值得存在；即便如此，也要配上一个正面目标，让注意力落在该做什么上。

## Pruning

- 让每个含义只有**一个权威来源（single source of truth）**：一个唯一权威的地方，这样改动这个行为就只需要改一处。**Duplication（重复）**——同一个含义出现在不止一个地方——会带来维护成本和 token 成本，还会把一个含义在这个阶梯上的显著程度抬高到超出它真实的等级。（这是主导词的意外反面——主导词是故意重复一个 token，从不重复含义。）
- **环境（environment）**本身也是一个权威来源——`package.json` 的 scripts、配置文件、目录结构、`--help` 的输出——一份复述它们的文档就是一个**缓存（cache）**：一份查询结果的副本，只有当这次查询成本很高时，它占用的加载成本才值得。缓存那些 agent 靠查看找不到的东西：没写下来的约定、一个选择背后的原因、任何配置都不会主动坦白的坑。把那些一个文件、一条命令就能查到的东西留给环境，它们在那里不会过时。
- 逐行检查**相关性（relevance）**：它是否依然和这份文档要做的事有关？一行内容会因为从来没和任务真正相关过（纯粹的铺陈，或者一个本该被外置的分支），或者因为它描述的行为或世界发生了变化而失去相关性。更短的文档更容易保持相关性。没有精简的纪律，默认的命运就是**沉积（sediment）**：陈旧的层一层层堆积，因为添加感觉安全、删除感觉危险，直到你不得不打穿这些层才能找到哪些还是活的。
- 逐句猎杀 **no-ops（空指令）**：一条模型本来就会默认遵守的指令，说了等于白说，却依然要花成本。检验标准——它相对*默认行为*是否真的改变了什么？——这是相对模型而言的，不是相对读者而言的：两个人对一条指令是不是 no-op 有分歧，本质上是对"默认行为是什么"有分歧，要靠实际跑一遍这份文档来裁定，而不是靠争论。当一句话没通过这个检验，就把整句话删掉，而不是删掉几个词。这个检验也能给主导词打分：一个弱到打不过默认行为的词（当 agent 本来就已经比较 thorough 时还说 _be thorough_）就是一个 no-op，修法是换一个更强的词（_relentless_），而不是换一种别的技巧。
