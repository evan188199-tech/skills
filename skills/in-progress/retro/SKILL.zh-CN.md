用户发起了**复盘（retrospective）**。你要为编码智能体的**环境**提出改进建议，让未来的运行更好。

## 步骤

1. 调用 Skill 工具加载 `writing-for-agents`，获取写作风格指南。

2. 阅读用户指定会话的一手资料。这可能需要在这台机器上检索会话日志；如果用户没有指定会话，默认取当前会话。

3. 在以下类别中寻找改进候选。

- **导航（Navigation）**：智能体找到正确文件容易吗？文件之间是否存在隐藏依赖？加一个**导航指针（navigation pointer）**会不会更省事？_适用时机_：会话花了很久才找到某条信息。
- **自动化检查**：有没有能拦住智能体错误的自动化检查？Lint、类型检查、测试、文件系统 linter？_适用时机_：智能体犯了一个本可被自动化检查抓住的错误。
- **编码规范**：要不要给**评审智能体**新增一条执行规则？要不要移除或澄清现有规则？_适用时机_：评审智能体没能发现某个错误。
- **全局 AGENTS.md**：有没有本应放进编码规范（或自动化检查）的引导指令？_适用时机_：AGENTS.md 过于庞大——无论在仓库还是用户全局范围。
- **工具经济性**：智能体有没有做过可以精简的高成本工具调用？有没有特别浪费 token 的自定义工具（CLI、MCP）？_适用时机_：智能体做了一次昂贵的工具调用。
- **无效指令（No-ops）**：查找引导文件里不影响智能体行为的指令。_适用时机_：引导文件臃肿难管。
- **信息可达性**：寻找提升智能体信息获取能力的机会，例如转发 dev server 日志、只读访问第三方服务。_适用时机_：某个关键信息智能体当时拿不到。

4. 按严重程度排序，把这些候选项呈现给用户。

## 参考

### 实现与评审

记住所有工作都经过两个阶段：实现和评审。实现智能体的**上下文压力**最大：它要负责探索、写代码和调试失败。

评审智能体的上下文压力最小：它拿到的是 diff，不需要探索，通常也不写代码、不调试。

这意味着应当由评审智能体负责落实编码规范，而不是实现智能体。

### 文件

你可以访问仓库中的这些文件：

- `CLAUDE.md`/`AGENTS.md`：这些文件会被推入在本仓库工作的任何智能体的上下文窗口。必须极度克制地使用，通常只放指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：这个文件在评审阶段读取，而非实现阶段。如果规范文件超过 1,000 行，增加指向 docs 目录的**导航指针**。
- Docs：把 docs 当作被其他文件指向的参考文件。写新文档前先找现有文档。
- Skills：文档适合做成 skill（因为其 description 会进入智能体上下文窗口），或用作用户主动调用的命令。具体遵循 `writing-for-agents` 技能中的建议。
