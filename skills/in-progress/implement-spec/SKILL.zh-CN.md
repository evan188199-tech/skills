你会拿到一份 spec。这份 spec 应当带有与之关联的工单（tickets），描述如何实现它。

目标是产出一个 PR，在单一分支上实现整份 spec。

这些工单不是步骤清单，而是一张带有阻塞关系的**任务图**。这意味着任何时刻都存在一批随时可认领的工单，即**前沿（frontier）**。

与子智能体（subagent）之间的通信应当尽量精简。主要通过**上下文指针（context pointers）**交流：指向 spec、工单、研究笔记和既往提交。不要复述指针已经能获取的信息。

**实现者子智能体（implementer subagents）**应尽可能在后台运行，以获得**最大并发**。

## 步骤

1. 阅读 spec 与工单，充分理解这张任务图。

2. （可选）使用**探索子智能体**完成工单所需的探索——相关代码文件或外部文档。确保探索子智能体可以保存文件：让它把 Markdown 笔记保存到仓库之外的目录，供后续所有子智能体访问。这样**实现者子智能体**就能专注于实现，而不是探索。

3. 创建分支和 draft PR。PR 应标记为「关闭」spec issue 及其工单。

4. 用**实现者子智能体**实现每张工单。每个实现者子智能体在自己的 worktree、自己的分支上工作。

5. 某个**实现者子智能体**完成后，用**合并子智能体（merger subagent）**把它的成果合并进 PR 分支。

6. 如果这改变了可用工单的**前沿**，就启动更多**实现者子智能体**去处理新工单，以保持最大并发。

7. 全部工单完成后，在 PR 分支上运行 /code-review，并用单个**实现者子智能体**修复评审提出的所有问题。

8. 将 PR 标记为 ready for review。

9. 清理所有**实现者子智能体**的 worktree。
