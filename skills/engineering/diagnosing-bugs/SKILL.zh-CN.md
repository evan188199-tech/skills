# Diagnosing Bugs

一套面向疑难 bug 的纪律。只有在有明确理由时才跳过某个阶段。

在探索代码库时，读取 `CONTEXT.md`（如果存在），建立对相关模块清晰的心智模型，并检查你所触碰区域的 ADR。

## Redact

这个 skill 会让你展示命令、输出和抓取到的 artifacts。**先脱敏所有 secrets**——在原处写上 `<REDACTED>`。围绕环境变量搭建循环，让凭证留在环境里，而不是出现在你展示的内容中。抓取到的 artifacts 里会带认证头：只引用真正带有信号的那几行。

如果脱敏后的输出不足以诊断这个 bug，明确说出来，并向用户求助。

## Phase 1 — 搭建一个反馈循环

**这就是这个 skill 的核心。** 其余一切都是机械性的。如果你有一个针对这个 bug **紧凑**的 pass/fail 信号——一个已经能在*这个* bug 上变红的信号——你就一定能找到原因；二分查找、假设验证和埋点都只是在消耗它。如果没有,再怎么盯着代码看也救不了你。

在这一步投入不成比例的精力。**要有攻击性，要有创造力，绝不轻易放弃。**

### 搭建方式——大致按这个顺序尝试

1. 在能触及这个 bug 的 seam 上写一个**失败测试**——unit、integration 或 e2e。
2. 针对一个跑着的开发服务器写 **curl / HTTP 脚本**。
3. 用一个 fixture 输入做 **CLI 调用**，把 stdout 和一份已知良好的 snapshot 做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，对 DOM/console/network 做断言。
5. **回放一份抓取到的 trace。** 把一次真实的网络请求 / payload / 事件日志存到磁盘上；在隔离环境下通过这段代码路径回放它。
6. **一次性 harness。** 拉起系统的一个最小子集（一个服务，mock 掉依赖），用一次函数调用触发这个 bug 所在的代码路径。
7. **Property / fuzz 循环。** 如果这个 bug 是"偶尔输出错误"，就跑 1000 个随机输入，寻找失败模式。
8. **二分查找 harness。** 如果这个 bug 是在两个已知状态之间（commit、数据集、版本）出现的，把"在状态 X 启动、检查、重复"这个过程自动化，这样你就能用 `git bisect run` 跑它。
9. **差异对比循环。** 用同样的输入分别跑旧版本和新版本（或两套配置），对比输出。
10. **HITL bash 脚本。** 最后手段。如果必须由人来点击，就用 `scripts/hitl-loop.template.sh` 来驱动*那个人*，这样这个循环依然是有结构的。抓取到的输出会反馈给你。

搭好正确的反馈循环，这个 bug 就已经解决了 90%。

### 收紧这个循环

把这个循环当作一个产品来对待。一旦有了*一个*循环，就**收紧**它：

- 能让它更快吗？（缓存搭建过程、跳过不相关的初始化、缩小测试范围。）
- 能让信号更清晰吗？（针对具体症状做断言，而不是"没崩溃就行"。）
- 能让它更确定吗？（固定时间、给随机数生成器设种子、隔离文件系统、冻结网络。）

一个 30 秒还会抽风的循环，几乎和没有循环没什么两样；一个 2 秒钟就能给出确定结果的循环才是紧凑的——那是调试的超能力。

### 不确定性 bug

目标不是一个干净的复现,而是一个**更高的复现率**。把触发条件循环跑 100 次、并行化、加压力测试、缩小时间窗口、注入 sleep。一个 50% 会抽风的 bug 是可调试的；1% 就不行了——持续提高复现率,直到它变得可调试为止。

### 当你确实搭不出一个循环时

停下来,明确说出来。列出你尝试过的东西。向用户请求：(a) 能复现问题的那个环境的访问权限,(b) 一份脱敏后抓取到的 artifact（HAR 文件、日志转储、core dump、带时间戳的录屏),或者 (c) 添加临时生产环境埋点的许可。**不要**在没有循环的情况下就贸然开始假设。

### 完成标准——一个能变红的紧凑循环

Phase 1 完成的标志是：这个循环是**紧凑的**且**具备变红能力**的：你能说出**一条命令**——一个脚本路径、一次测试调用、一次 curl——它是你**已经至少运行过一次**的（展示这次调用及其输出,脱敏后),并且满足：

- [ ] **具备变红能力**——它驱动的是真正的 bug 代码路径,并断言的是**用户描述的确切症状**,所以它能在这个 bug 上变红,修复后变绿。不是"运行时不报错"——它必须能*捕捉到这个具体的 bug*。
- [ ] **确定性**——每次运行结果一致（对不确定性 bug：如上所述,复现率被固定在一个较高的水平)。
- [ ] **快**——是秒级,不是分钟级。
- [ ] **agent 可运行**——你能无人值守地运行它；只有通过 `scripts/hitl-loop.template.sh` 才能把人纳入循环。

如果你发现自己在这条命令存在之前就已经在读代码、构建理论,**停下来——直接跳到假设正是这个 skill 要阻止的那种失败。** 没有具备变红能力的命令,就不能进入 Phase 2。

## Phase 2 — 复现 + 最小化

运行这个循环。看着它变红——bug 出现了。

确认：

- [ ] 这个循环产生的失败模式,是**用户**描述的那个——而不是一个碰巧相似的另一个失败。抓错 bug = 修错方向。
- [ ] 这个失败在多次运行中都能复现（对于不确定性 bug,复现率要高到足以用来调试)。
- [ ] 你已经抓取到确切的症状（错误信息、错误输出、缓慢的耗时),这样后续阶段才能验证修复是否真的解决了它。

### 最小化

一旦它变红,把复现场景收缩到**依然能变红的最小场景**。**一次只砍一样**——输入、调用方、配置、数据、步骤——每砍一样就重新跑一次循环——只保留对这个失败真正有支撑作用的部分。

为什么要这么做：一个最小复现场景能缩小 Phase 3 里的假设空间（需要怀疑的活动部件更少了),并会成为 Phase 5 里那个干净的 regression test。

完成的标志是**剩下的每一个元素都是有支撑作用的**——去掉任何一个,循环就会变绿。

在你完成复现**且**最小化之前,不要继续往下走。

## Phase 3 — 提出假设

在测试任何一个假设之前,先生成 **3-5 个排好序的假设**。只生成单一假设会让你锚定在第一个看起来合理的想法上。

每个假设都必须是**可证伪的**：说明它做出的预测。

> 格式："如果 <X> 是原因,那么<改变 Y> 会让这个 bug 消失 / <改变 Z> 会让它变得更糟。"

如果你说不出这个预测,说明这个假设只是一种直觉——要么丢弃,要么把它磨得更锋利。

**在测试之前,把这份排好序的列表展示给用户。** 他们往往拥有能立刻重新排序的领域知识("我们刚给 #3 部署了一次改动"),或者知道哪些假设已经被排除过了。这是一个便宜的检查点,能省下大量时间。但不要卡在这一步——如果用户不在,就按你自己的排序继续。

## Phase 4 — 埋点

每个探针都必须对应 Phase 3 里的一个具体预测。**一次只改变一个变量。**

工具优先级：

1. 如果环境支持,优先用 **调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能区分各假设的边界处打**有针对性的日志**。
3. 永远不要"把所有东西都记下来然后 grep"。

**给每一条调试日志打上标签**,用一个唯一前缀,例如 `[DEBUG-a4f2]`。这样最后的清理工作就变成一次 grep。没打标签的日志会被遗留下来;打了标签的日志会被清理掉。

**性能分支。** 对于性能回退,日志通常没什么用。改为：先建立一个基线测量（计时 harness、`performance.now()`、profiler、查询计划),然后做二分查找。先测量,后修复。

## Phase 5 — 修复 + regression test

**在修复之前**先写 regression test——但前提是存在一个**正确的 seam**。

一个正确的 seam,是指测试能在调用点真正复现这个 **bug 的真实模式**。如果唯一能用的 seam 太浅（当 bug 需要多个调用方时却只有单调用方测试、无法复现触发这个 bug 的调用链的单元测试),在那里写 regression test 只会给出错误的信心。

**如果不存在正确的 seam,这本身就是一项发现。** 记下它。代码库的架构正在阻止这个 bug 被真正锁定。把它标记出来,留给下一个阶段。

如果存在正确的 seam：

1. 把最小化后的复现场景变成那个 seam 上的一个失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 针对原始（未最小化）的场景重新跑一次 Phase 1 的反馈循环。

## Phase 6 — 清理 + 事后复盘

在宣布完成之前,必须完成：

- [ ] 原始复现场景不再复现（重新跑一次 Phase 1 的循环)
- [ ] Regression test 通过（或者已经记录了"没有可用 seam"这一事实)
- [ ] 所有 `[DEBUG-...]` 埋点都已移除（grep 那个前缀确认)
- [ ] 一次性 prototype 已删除（或者移到一个明确标记的调试专用位置)
- [ ] 最终被证实正确的那个假设,已经写进 commit / PR 信息里——好让下一个调试的人也能学到

**然后问自己：什么东西本可以防止这个 bug 发生？** 如果答案涉及架构层面的改动（没有好的测试 seam、纠缠不清的调用方、隐藏的耦合),就把具体情况交接给 `/improve-codebase-architecture` skill。**在**修复落地之后再给出这个建议,而不是之前——此刻你掌握的信息比开始时更多。
