# ADR Format

ADR 存放在 `docs/adr/` 下，使用连续编号：`0001-slug.md`、`0002-slug.md`，以此类推。

按需创建 `docs/adr/` 目录——只在第一次需要 ADR 时创建。

## Template

```md
# {决策的简短标题}

{1-3 句话：背景是什么，我们决定了什么，以及为什么。}
```

就这么多。一份 ADR 可以只有一段话。它的价值在于记录下*确实做过*一个决策，以及*为什么*——而不在于填满各个小节。

## Optional sections

只在这些小节确实能带来价值时才加上。大多数 ADR 都用不上它们。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——当决策会被重新审视时有用
- **Considered Options**——只在那些被否决的备选方案值得被记住时才写
- **Consequences**——只在有不明显的下游影响需要特别指出时才写

## Numbering

扫描 `docs/adr/`，找到现有最大的编号，加一。

## When to offer an ADR

以下三点必须同时成立：

1. **难以撤销**——之后改变主意的代价是实实在在的
2. **没有上下文就会让人意外**——未来的读者看到这段代码会想"他们当初到底为什么要这么做？"
3. **是一次真实权衡的结果**——存在真正的备选方案，而你出于具体原因选了其中一个

如果一个决策很容易撤销，就跳过它——反正你之后会撤销它。如果它并不令人意外，就不会有人纳闷为什么。如果根本没有真正的备选方案，除了"我们做了显而易见的事"之外没什么可记录的。

### What qualifies

- **架构形态。** "我们用的是 monorepo。" "写模型是 event-sourced 的，读模型被投影进 Postgres。"
- **context 之间的集成模式。** "Ordering 和 Billing 之间通过领域事件通信，而不是同步 HTTP。"
- **带有锁定效应的技术选型。** 数据库、消息总线、认证提供方、部署目标。不是每一个库都要记——只记那些换掉需要花一个季度的。
- **边界和范围决策。** "Customer 数据由 Customer context 拥有；其他 context 只通过 ID 引用它。" 明确的"不做什么"和"做什么"同样有价值。
- **刻意偏离显而易见路径的决定。** "我们用手写 SQL 而不是 ORM，因为 X。" 任何一个理性的读者会假设你选了相反做法的地方。这些记录能防止下一个工程师去"修正"一个本来就是刻意为之的决定。
- **代码里看不出来的约束。** "出于合规要求我们不能用 AWS。" "因为合作方 API 的合约要求，响应时间必须在 200ms 以内。"
- **被否决的备选方案，且否决理由不明显时。** 如果你考虑过 GraphQL，出于一些细微原因选了 REST，把它记下来——否则六个月后又会有人重新提议用 GraphQL。
