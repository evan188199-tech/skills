# Logic Prototype

一个单一、自包含的 HTML 文件——一个**可分享的演示**——让任何人都能通过点按钮来驱动一个 state 模型。当问题关于**业务逻辑、state 转换，或数据形状**时用这种形式——那种在纸面上看起来合理、但只有把它推过真实场景才会发现不对劲的东西。

因为它是一个不需要安装任何东西的单文件，你可以把它交给一个非开发者——设计师、PM、领域专家——让他们亲自感受这个模型。所以它要说他们的语言，而不是代码的语言。

## When this is the right shape

- "我不确定这个 state machine 能不能处理先 X 后 Y 的边界情况。"
- "这个数据模型真的能表示……这种情况吗？"
- "我想在写 API 之前先感受一下它应该长什么样。"
- 任何"想按按钮、看着 state 变化"的场景。

如果问题是"这个应该长什么样"——选错分支了。用 [UI.md](UI.md)。

## Process

### 1. State the question

在写代码之前，先写下你在为哪个 state 模型、哪个问题做 prototype。一段话，放在演示的最上方（在一段醒目的介绍里，不只是注释）。一个回答错误问题的逻辑 prototype 纯属浪费——把问题写明白，这样以后不管用户是在场还是回来重新看，都能核对它。

### 2. Isolate the logic in a portable module

把真正的逻辑——回答这个问题的那部分——放进一个 `<script>` 块里，写成一个小的、纯粹的模块，将来可以直接拿出来放进真正的代码库。它周围的页面是一次性的；这个模块不是。

具体形状取决于问题：

- **一个纯 reducer** —— `(state, action) => state`。适合动作是离散事件、state 是单一值的情况。
- **一个 state machine** —— 显式的 states 和 transitions。适合"现在到底哪些动作是合法的"本身就是问题一部分的情况。
- **一小组针对纯数据类型的纯函数**。适合没有隐式当前 state、只有变换的情况。
- **一个方法面清晰的 class 或模块**，适合逻辑确实拥有持续存在的内部 state 的情况。

挑选最适合这个问题本身的形状，*而不是*最容易接到页面上的那个。保持它的纯粹：不碰 DOM，不用 `document`，不让按钮事件处理伸手进去。页面调用它；反方向绝不会有数据流动。这正是让这个 prototype 在自己的生命周期结束后依然有用的原因：一旦问题有了答案，这个被验证过的 reducer / machine / 函数集就能自己直接搬进真正的模块。

### 3. Build the shareable HTML file

一个文件，纯 HTML/CSS/JS——不用框架、不用打包器、不用服务器，全部内联，这样双击就能打开，转发邮件也不会坏。任何人打开它都应该能直接运行。

为非开发者而写。每个标签都用**领域语言**，不是代码——按钮和 state 读起来像业务描述，不像 reducer。用大白话解释发生了什么。

按从上到下的清晰层次布局：

1. **标题和一行说明**，说明这个演示能让你探索什么（第 1 步里的那个问题）。
2. **Current state** —— 完整的相关 state，渲染成一个可读的面板（带标签的字段，不是原始 JSON 转储），每次点击后都重新渲染，让变化清晰可见。在有助于非开发者理解的地方，特别指出刚刚发生了什么变化。
3. **Free-play buttons** —— 每个动作一个按钮，始终可用，这样任何人都能以任意顺序摆弄这个模型。每次点击都会派发对应的动作，并重新渲染 state。
4. **Guided walkthroughs** —— 一组**场景（scenarios）**，一个标签页一个。每个标签页都有一段简短的大白话描述，说明这个场景设定了什么情况、要留意什么——下面是这个场景要按顺序点击的**按钮**。每一步都是一个真实的按钮：点击它就会执行那个动作，并进入下一步。开始一次 walkthrough 会重置到一个已知的初始 state，这样每次跑这个场景的过程都一样。

挑选那些能展示棘手情况的场景——正常路径、一个刁钻的边界情况、一次本该不被允许的尝试——那些在纸面上很难推理清楚的场景。

保持美观但克制：干净的排版、充足的间距、一个强调色。不要动画，不要花哨的东西——不要有任何跟 state 和按钮抢注意力的元素。

### 4. Hand it over

把文件发给他们，或者替他们打开。他们会在有空时点着 walkthroughs 走一遍、也会自己随意摆弄；真正有意思的时刻是他们说"等等，这不应该发生"或者"咦，我以为 X 会不一样"——那些正是*想法*里的 bug，这正是整件事的意义所在。如果他们想要新的动作或新的场景，就加上去。Prototype 是会演进的。

### 5. Capture the answer and the prototype

一旦这个 prototype 回答了它的问题，先保存这个答案，再按照 [SKILL](SKILL.md) 描述的方式保存这个 prototype 本身。针对逻辑场景的具体映射：被验证过的 reducer / machine / 函数集会被吸收进真正的模块（决策被吸收）；HTML 外壳会跟着一起进入那个把 prototype 保留为主源头的一次性分支——而且因为它是一个自包含文件，在那里它依然能轻松地重新运行。

## Anti-patterns

- **不要加测试。** 一个需要测试的 prototype 就已经不再是 prototype 了。
- **不要接到真实数据库上。** 除非问题明确关于持久化，否则用内存 state。
- **不要泛化。** 不要考虑"如果以后我们想支持 X 呢"。这个 prototype 只回答一个问题。
- **不要把逻辑和页面混在一起。** 如果那个纯模块引用了 DOM、`document` 或按钮事件处理，它就不再能被直接拿走了。让页面保持成一个盖在纯模块之上的薄壳。
- **不要动用框架、打包器或服务器。** 一个接收方双击就能打开的文件；一个 React 应用或开发服务器会毁掉"可分享"这个属性。
- **不要把 HTML 外壳发布到生产环境。** 这个页面是为手动点击而优化的。它背后的逻辑模块才是值得保留的部分。
