# Prototype

一个 prototype 是**回答一个问题的一次性代码**。这个问题决定它的形状。

## Pick a branch

先确定要回答的是哪个问题——从用户的提问、周边代码，或者直接问在场的用户：

- **"这个逻辑/state 模型感觉对不对？"** → [LOGIC.md](LOGIC.md)。构建一个可分享的单一 HTML 文件——free-play 按钮加上分标签页的引导式演练——用来把这个 state machine 推过那些在纸面上很难推理清楚的场景，而且要让非开发者也能操作。
- **"这个应该长什么样？"** → [UI.md](UI.md)。在同一个路由上生成几种截然不同的 UI 变体，通过一个 URL search param 和一个浮动底栏来切换。

这两个分支产出的 artifact 非常不同——选错了会浪费整个 prototype。如果这个问题确实模糊、用户又联系不上，就默认选更贴近周边代码的那个分支（后端模块 → logic；页面或组件 → UI），并在 prototype 顶部写明这个假设。

## Rules that apply to both

1. **从第一天起就是一次性的，并且清楚地标明这一点。** 把 prototype 代码放在它实际会被用到的地方附近（挨着它正在为之做原型的模块或页面），让上下文一目了然——但要用一个让随手一看的人也能认出"这是个 prototype，不是生产代码"的名字。对于一次性的 UI 路由，遵循项目已有的路由约定；不要发明一套新的顶层结构。
2. **运行起来毫不费力。** 一个 UI prototype 应该从项目任务运行器里的一条命令启动——`pnpm <name>`、`python <path>`、`bun <path>` 等等。一个逻辑演示是用户双击就能打开的单个 HTML 文件。不管哪种，启动它都不该需要动脑子。
3. **默认不持久化。** State 存在内存里。持久化是这个 prototype 正在*验证*的东西，不该是它依赖的东西。如果问题明确涉及数据库，就用一个 scratch DB 或本地文件，并起一个清楚标明 "PROTOTYPE — wipe me" 的名字。
4. **跳过打磨。** 不写测试，除了让 prototype *能跑起来*所必需的之外不做任何错误处理，不做抽象。重点是快速学到点什么。
5. **把 state 亮出来。** 每次操作之后（logic）或每次切换变体时（UI），把完整的相关 state 打印或渲染出来，让用户能看到发生了什么变化。
6. **完成后把它保存下来。** 把任何被验证过的决策折叠进真正的代码，然后把 prototype 本身作为一个**主源头（primary source）**保存下来：把它提交到一个从 main 分出的一次性分支上，并在 implementation issue 上留一个指向那个分支的上下文指针。答案本身——结论以及它解决的那个问题——也要记录在 issue 或一次 commit 里。Main 分支只保留那个被验证过的决策。
