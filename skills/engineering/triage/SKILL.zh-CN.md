# Triage

让项目 issue tracker 上的 issues，在一套小型的 triage roles 状态机里流转。

如果这个仓库把外部 pull request 当作一个 request surface 来处理（见 issue-tracker 配置），triage 也覆盖它们：**一个 PR 就是一个带着代码的 issue**——同样的 roles、同样的 states、同样的状态机，下面标注了几处 "for a PR" 的差异。按 tracker 配置，把一个裸的 `#42` 解析成一个 issue 或 PR。

Triage 过程中发到 issue tracker 上的每一条评论或 issue，**必须**以这句免责声明开头：

```
> *This was generated by AI during triage.*
```

- [AGENT-BRIEF.md](AGENT-BRIEF.md) —— 如何写出经得起时间考验的 agent briefs
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) —— `.out-of-scope/` 知识库是怎么运作的

## Roles

两个**分类（category）** roles：

- `bug` —— 有东西坏了
- `enhancement` —— 新功能或改进

五个**状态（state）** roles：

- `needs-triage` —— 维护者需要评估
- `needs-info` —— 正在等待报告者提供更多信息
- `ready-for-agent` —— 已完全说明清楚，可以交给一个 AFK agent
- `ready-for-human` —— 需要人类来实现
- `wontfix` —— 不会被处理

对于一个 PR，同样的状态是针对所附代码而言的：`ready-for-agent` 意味着已经附上了一份 brief，agent 应该在这份 diff 上采取下一步行动；`ready-for-human` 意味着可以由人类合并了。

每个经过 triage 的 issue 应该恰好带有一个 category role 和一个 state role。如果 state roles 冲突，先标记出来，在做任何其他事之前问一下维护者。

这些都是规范角色名——issue tracker 里实际使用的 label 字符串可能不同。这份映射应该已经提供给你了——如果没有，运行 `/setup-matt-pocock-skills`。

State transitions：一个没打 label 的 issue 通常先进入 `needs-triage`；从那里可以转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦报告者回复，`needs-info` 就回到 `needs-triage`。维护者可以随时覆盖——如果某次转换看起来不寻常，先标记出来，在继续之前问一下。

## Invocation

维护者调用 `/triage`，用自然语言描述他们想要什么。理解这个请求并采取行动。例如：

- "Show me anything that needs my attention"
- "Let's look at #42"（issue 或 PR）
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

查询 issue tracker，展示三个分组，从最旧的开始：

1. **Unlabeled** —— 从没做过 triage 的。
2. **`needs-triage`** —— 评估正在进行中的。
3. **`needs-info` 且自上次 triage notes 以来报告者有新动态的** —— 需要重新评估。

当 PR 也在范围内时，把外部 PR 也纳入这些分组，并在每一行标上 `[PR]` 或 `[issue]`。发现阶段只展示*外部* PR（谁算"外部"由 tracker 配置定义）——协作者进行中的 PR 不算 triage 工作。这个过滤只在发现阶段生效；一个被明确点名的 PR 无论作者是谁都会被 triage。

展示每一项的数量和一行摘要。让维护者来挑。

## Triage a specific issue or PR

1. **Gather context。** 读完整的 issue 或 PR（正文、评论、labels、作者、日期；如果是 PR，还要读 diff）。解析任何之前的 triage notes，这样就不会重复问已经解决的问题。用项目的领域词汇表探索代码库，尊重相关区域的 ADR。对代码库做两项检查：(a) **redundancy**——按领域概念（不只是按请求的措辞）搜索是否已经存在对应行为的实现，并报告你查看过哪里。如果找到了，这就是一个已经实现的 `wontfix`（第 5 步）。(b) **prior rejection**——读 `.out-of-scope/*.md`，找出任何和这个请求相似的记录。

2. **Recommend。** 把你的 category 和 state 建议以及理由告诉维护者，外加一份和这个请求相关的简短代码库摘要——包括它是否已经被实现了。等待指示。

3. **Verify the claim。** 在做任何 grilling 之前，先检查这个说法是否站得住脚。对于一个 bug，按报告者的步骤复现它。对于一个 PR，确认这份 diff 确实做到了它声称的事——checkout 它，跑相关的测试或命令。报告发生了什么：确认成立（附上代码路径）、验证失败，或者细节不足（这是一个很强的 `needs-info` 信号）。一次已确认的验证能让 agent brief 强得多。

4. **Grill（如果需要）。** 如果这个请求需要被进一步充实，一起运行 `/grilling` 和 `/domain-modeling` skills——一轮一轮问题地把它梳理成形，同时打磨领域术语，随着决策落地就地更新 `CONTEXT.md`/ADR。

5. **Apply the outcome：**
   - `ready-for-agent` —— 发一条 agent brief 评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` —— 结构和 agent brief 一样，但要注明为什么它不能被委托出去（判断性决策、外部访问权限、设计决策、手动测试）。
   - `needs-info` —— 发 triage notes（模板见下文）。
   - `wontfix` —— 关闭，评论内容取决于*原因*：
     - **已经实现了** —— 这个改动在代码库里已经存在了。指出它在哪里；**不要**写进 `.out-of-scope/`（那个知识库是给*被否决*的请求用的，不是给已经做出来的东西用的）。
     - **被否决（bug）** —— 礼貌地解释，然后关闭。
     - **被否决（enhancement）** —— 写进 `.out-of-scope/`，在评论里链接过去，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` —— 应用这个 role。如果有部分进展，可以选择性地评论。

## Quick state override

如果维护者说 "move #42 to ready-for-agent"，相信他们，直接应用这个 role。先确认你即将做的事（role 变更、评论、关闭），再行动。跳过 grilling。如果是在没有 grilling session 的情况下转到 `ready-for-agent`，问一下他们是否想写一份 agent brief。

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把 grilling 过程中已经解决的一切都记在 "established so far" 下面，这样这些工作不会丢失。问题必须具体、可操作，不能是"please provide more info"这种。

## Resuming a previous session

如果这个 issue 或 PR 上已经有之前的 triage notes，读它们，检查报告者是否已经回答了任何悬而未决的问题，在继续之前展示一份更新后的情况。不要重复问已经解决的问题。
