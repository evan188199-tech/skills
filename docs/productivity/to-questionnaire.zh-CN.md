## What it does

`to-questionnaire` 把一个你一个人解决不了的决策,变成一份**问卷**——一份 Markdown 文档,交给唯一拥有你所缺信息的那个人,让他们异步填写,或者两人一起在会上过一遍。

它盘问的是**怎么发送**,从不是主题本身。就主题采访你在这里毫无意义:你不了解这个主题,正是你要写给别人的原因。所以它问那两件你永远能回答的事——发给谁、你需要从他们那里拿回什么——然后把文档里的每一个问题都对准这两者之间的**缺口**。

## When to reach for it

你需要输入 `/to-questionnaire` 来调用它——[agent](https://www.aihero.dev/ai-coding-dictionary/agent) 不会自己主动使用它。

当一个决策卡在只存在于另一个人脑子里的知识上时用它:一个客户、一位领域专家、一位掌管业务规则的高管、一个不在你团队里的同事。你想要哪个 skill,取决于答案实际在哪里:

| 答案在… | 该用什么 |
| --- | --- |
| 你自己脑子里,还没打磨过 | [grill-me](https://aihero.dev/skills-grill-me) |
| 代码库里 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 别人脑子里 | `to-questionnaire` |
| 还没人知道——这个问题需要一个可以反应的东西 | [prototype](https://aihero.dev/skills-prototype) |

常见的情况是一次 [grilling](https://www.aihero.dev/ai-coding-dictionary/grilling) session 卡住了:浮现出来的一些东西不该由你来回答。在同一段对话里跑 `/to-questionnaire`,把那些问题挪到线下,再把答案带回来,继续。

## The send, not the subject

这场访谈只有两次交流,然后就停下。

- **发给谁?** 他们的角色、他们的专业领域、他们和你的关系。这决定了这份文档的语气,以及它要携带多少背景信息——一个外部客户需要被带入状态,一个队友不需要。
- **你需要拿回什么?** 你一个人解决不了的具体决策或事实。这会变成最终文档要对照的检查清单:你点名的每一项,都会有一个对准它的问题。

之后的一切都是起草。文件落在当前目录下的 `to-questionnaire-<slug>.md`。没有 setup,没有工作区,没有什么要配置的。

## The document

它被框定为一份**探索式问卷**——你缺乏背景信息,收件人拥有它——这个框架决定了它的形状:

- 一行说明这份问卷牵涉的决策,一段简短的背景介绍,给一个从没在你脑子里待过的收件人。
- 问题按**最重要的排最前**排序,归到有主题的标题下,因为异步意味着你可能只有一次机会。
- 每个问题一个想法,绝不复合提问,下面附一个待填写的答案占位,只有当一个问题可能被误读时才加一行 *why this matters*。
- 明确允许回答"我不知道"——一个被标出来的不确定性是有用的;一个听起来像事实的自信猜测不是。
- 结尾的兜底问题:还有什么我们没问到、但该知道的?

它刻意不是两样东西。它不是**分支式**的——这些问题是一份扁平的、分组的列表,不是一棵"如果你答了 A 就跳过 D 节"的树。它也不是**多收件人**的——一次运行为一个人产出一份文档。

## Common questions

**它会读我的 grilling session、从里面提取问题吗?**
不会作为一个独立步骤。这个 skill 没有摄入阶段:它先问关于发送的问题,然后起草。让它在一次 grilling session 之后依然有效的原因是,你是在**同一段对话**里运行它的,所以那次 session 已经在 [context](https://www.aihero.dev/ai-coding-dictionary/context) 里了,起草能直接借用它。在一个全新 session 里启动它,它对那次 grilling 一无所知——回答"你需要拿回什么"时,你得自己重新把主题喂给它。

**缺失的答案不都在同一个人身上。它能按收件人拆分吗?**
不能。第一步问的是*那个*收件人,单数,整份文档的语气和背景都是针对他们定制的。如果三个人各自拥有答案的一部分,就跑三次,一人一次。在单份文档内部按学科或角色路由问题,是人们提出过的诉求;但不是已发布的功能。

**这些问题是有依赖关系的吗——它会根据更早的答案跳过某些小节吗?**
不会。有依赖关系的问题设计被探索过,但没有发布。产出是一份静态文档:有主题的分组,最重要的排最前,每个问题都在场。反对这么做的理由很充分——一个提前规划超过两三个问题、却还没拿到真实答案的 [model](https://www.aihero.dev/ai-coding-dictionary/model) 规划得不会好,而一份带分支的文档必须为每一个答案提前规划所有分支。

**如果收件人也不知道怎么办?**
这份文档会告诉他们说出来。"我不知道"和部分回答是被明确要求的,一个被标出来的不确定性,比一个猜测更有价值,因为一旦回到你的 context 里,一个模糊的答案和一个自信却错误的答案看起来是一样的。

**它会把这份文档发到哪里吗——Slack、issue tracker、邮件?**
不会。它在当前目录里写一份 Markdown 文件,告诉你路径。怎么发是你的事:粘进一个 [ticket](https://www.aihero.dev/ai-coding-dictionary/ticket)、扔进一个 Slack 讨论串、附到一封邮件里,或者在共享屏幕上打开、现场过一遍。这四种方式都有人手动接过。

**这不就是批量模式的 `/grill-me` 吗?**
不是,这个区别值得记住。`grill-me` 已经是按**轮次**提问的——一次问完整个 frontier,再根据你的答案重新计算——所以"一次给我所有问题"这个诉求已经被那边满足了。`to-questionnaire` 关心的是一个不同的维度:不是问题怎么被发出去,而是答案在谁的脑子里。自己更快地回答它们是 `grill-me`;把它们从别人那里挖出来是这个。

**我不能直接让 agent 帮我做这个吗,不用一个专门的 skill?**
可以,而且在它出现之前很多人就是这么做的——`OPEN_QUESTIONS.md` 文件、发给客户的表格、每个未回答问题对应一张"需要更多信息"的 ticket。这个 skill 买到的是两样东西:这场访谈永远不会漂移到主题本身上,而且产出的文档是一个非技术收件人真的能填的形状。如果你已经有一套好用的固定格式,诚实的答案是你不需要这个。

## It's working if

- 它问了关于收件人、以及你需要拿回什么的问题,然后就停止提问了。一个关于主题本身的问题,说明这个 skill 已经跑偏了。
- 你点名的每一项"我需要拿回什么",都能在文件里追溯到一个对应的问题。
- 这些问题读起来是瞄准*收件人*知道什么,而不是把你自己悬而未决的问题原样抄下来。
- 你能把这份文件交给一个没参与过这段对话的人,他们能明白自己为什么收到它、该在什么时候之前回复。
- 拿回来的答案是能直接喂给新一轮 grilling 的可用素材,而不是一堆新的问题。

## Where it fits

`to-questionnaire` 是一个随时可用的独立工具。它坐在你自己知识的边界上,那里下一步是另一个人,而不是另一个 skill——最常见于 flow 进行到一半、规划卡在一件不该由你决定的事情上时。

它的邻居是 [grill-me](https://aihero.dev/skills-grill-me),两者的区别在于答案活在哪里:grilling 挖掘的是你,一份问卷挖掘的是别人。拿回来的东西是原始素材——把它喂进新一轮 grilling,或者如果这项工作正走向构建,喂进 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)。当你拿不准此刻该用哪个 skill 时,[ask-matt](https://aihero.dev/skills-ask-matt) 会帮你路由。
